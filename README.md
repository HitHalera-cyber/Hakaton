# Прогнозирование внешних рисков и планирование ВКД на МКС

Исследовательский прототип поддержки решений для специалиста наземной группы планирования внекорабельной деятельности (ВКД/EVA) на МКС. Сервис самостоятельно получает открытые данные, оценивает не менее двух независимых механизмов внешнего воздействия, сравнивает окна проведения работ одинаковой длительности и объясняет каждую рекомендацию со ссылкой на источник, время публикации и применённое правило.

Сделано для серии соревнований «КосмоХакатон 2026» (постановка задачи и критерии оценки — см. `docs/` при наличии, либо файлы, приложенные к заданию).

> Допуск к реальной ВКД остаётся за уполномоченными специалистами. Это исследовательский прототип поддержки решений, а не система, принимающая решение за человека.

## Что показывает сервис

1. Пользователь задаёт режим (текущая обстановка / историческая дата 01.05.2024–30.06.2024), начало и длительность ВКД (1–8 ч) и период поиска альтернативного начала (до 24 ч).
2. Сервис рассчитывает траекторию МКС по орбитальным элементам (SGP4), получает и оценивает два независимых механизма воздействия:
   - **Космическая погода** — радиационные бури (S-scale, определяющий фактор дозы при ВКД), с геомагнитной обстановкой (G) и радионарушениями (R) как ограниченным контекстом, не увеличивающим риск повторно.
   - **Сближения и MMOD** — прокси-показатель по каталогизированным сближениям (CelesTrak SOCRATES) как индикатор обстановки по мусору вокруг станции.
3. Сравнивает не менее двух окон одинаковой длительности, объясняет, какие факторы и интервалы определили выбор, и честно обрабатывает случаи нехватки данных или равнозначных вариантов.
4. Для каждого предупреждения показывает: величину и её значение для ВКД, период (набл./ожид.), источник и время публикации, применённое правило, ограничения и обоснование уверенности — с визуальным различием наблюдения / внешнего прогноза / расчёта команды.
5. Пользователь сохраняет и выгружает результат (JSON + CSV в одном архиве) с параметрами запроса, моментом отсечения, версией алгоритма и ссылками на источники.

## Архитектура

```
backend/app/
  config.py         — все настройки и константы задачи (единое место)
  models.py         — pydantic-схемы (Signal, FactorAssessment, WindowAssessment, ...)
  cache.py          — дисковый кеш с TTL, заморозкой/отключением источника (надёжность)
  http.py           — общий httpx-клиент
  orbit_math.py     — TEME->ECEF, геодезические координаты, положение Солнца, тень Земли
  orbit.py          — получение TLE/GP и SGP4-пропагация траектории
  clients/          — celestrak.py, swpc.py, donki.py, spacetrack.py (сырые запросы к источникам)
  factors/
    space_weather.py — механизм №1 (обязательный): космическая погода, включая
                        строгий "прогноз из прошлого" по времени публикации DONKI
    conjunction.py    — механизм №2: сближения/MMOD (CelesTrak SOCRATES)
  analysis.py        — сравнение окон, взвешивание факторов, рекомендация
  experiments.py      — критерий Т5: сравнение с наивным базовым методом
  export.py          — сохранение расчёта на диск и сборка выгрузки (JSON+CSV+README)
  api.py / main.py    — FastAPI-приложение
frontend/            — статический одностраничный интерфейс (Leaflet + three.js, без сборки)
tests/               — pytest: SGP4, кеш/надёжность, отсечение по времени, движок сравнения
```

Расчёты, получение данных и интерфейс разделены (критерий Т7): `clients/` не знает о бизнес-правилах, `factors/`+`analysis.py` не делают HTTP-запросов напрямую (только через `cache.py`), `api.py` — только маршрутизация и валидация.

## Источники данных

| Источник | Что берём | Единицы / формат | Частота обновления | Ограничения |
|---|---|---|---|---|
| CelesTrak GP (`gp.php`) | Текущие орбитальные элементы МКС (NORAD 25544), формат TLE | безразмерные элементы TLE, эпоха в сутках года | несколько раз в сутки | не даёт истории; для прошлого используется реконструкция или Space-Track; если недоступен — автопереход на зеркало/Space-Track (см. ниже) |
| Зеркало TLE на GitHub (fallback) | Republish тех же элементов CelesTrak через `raw.githubusercontent.com` | TLE | каждые ~8 часов (GitHub Action) | не независимый источник, только для отказоустойчивости; не требует аккаунта |
| Space-Track GP / GP_HISTORY (опционально) | Текущие и исторические орбитальные элементы | TLE + `CREATION_DATE`/`EPOCH` | по мере публикации | требует учётной записи; явно необязателен по условиям задачи; для текущей орбиты используется только как резервный источник |
| NOAA SWPC `noaa-scales.json` | Шкалы S (радиация), G (геомагнитная буря), R (радионарушение) | 0–5, посуточно (сегодня/+1..+3 суток) | публикуется NOAA несколько раз в сутки | посуточная гранулярность грубее горизонта 6 ч — время помечается как приблизительное |
| NOAA SWPC `alerts.json` | Активные оповещения с текстом и временем публикации | текст + `issue_datetime` | по мере событий | текст не формализован, используется как вспомогательный сигнал |
| NASA DONKI `notifications` | Датированные уведомления о SEP/GST/RBE/CME/FLR с `messageIssueTime` | текст + тип + время публикации | по мере событий, с 2024 г. в архиве | в историческом режиме — обязательный источник для строгого "прогноза из прошлого" (см. ниже); в режиме «Текущая обстановка» — независимый источник в дополнение к NOAA SWPC, без отсечения по времени, покрывает весь запрошенный период ВКД, а не только "сегодня/завтра" |
| NASA DONKI `GST`/`SEP` | Структурированные события (используются только в эксперименте/проверке) | числовые Kp/время | по мере событий | не несут поля времени публикации, поэтому не участвуют в расчёте с отсечением |
| CelesTrak SOCRATES | Расчётные сближения каталогизированных объектов с МКС | TCA, минимальная дальность (км), вероятность | обновляется несколько раз в сутки, окно ~7 суток вперёд | нет практичного датированного архива без Space-Track → в историческом режиме фактор честно помечается недостатком данных, а не нулевым риском; если недоступен в текущем режиме — автопереход на Space-Track `cdm_public` (см. ниже) |
| Space-Track `cdm_public` (опционально, fallback) | Официальные Conjunction Data Message для станции — резерв на случай недоступности SOCRATES | TCA, `MISS_DISTANCE` (метры → переводится в км), вероятность столкновения | по мере публикации CDM | требует учётной записи; названия полей схемы **не** захардкожены — перед каждым запросом читаются "вживую" через `modeldef` (см. `clients/spacetrack.py`), поэтому сигналы с этого источника помечены пониженной уверенностью |

Два источника, перепечатывающих одно измерение, не считаются независимым подтверждением — используется по одному первичному источнику на механизм. Коммерческие данные не требуются: все перечисленные источники открытые (DONKI работает и с бесплатным `DEMO_KEY`).

## Два механизма воздействия (критерий О1)

1. **Космическая погода** (обязательный). Наблюдаемая величина — уровень солнечной радиационной бури (S-scale/поток протонов >10 МэВ), напрямую связанный с дополнительной дозой облучения космонавта вне защиты станции при ВКД. Внутри одного фактора объединены и вспышки на Солнце (FLR/CME из DONKI), и радиация как их прямое следствие (S-scale/SEP) — намеренно не разнесены на отдельные факторы, так как это причина и следствие одного физического механизма, а не два независимых. G/R-scale учитываются как контекст с ограниченным вкладом (см. `factors/space_weather.py`, правило `_CONTEXT_CAP`), чтобы связанные сигналы одного солнечного события не удваивали риск.
2. **Сближения/MMOD**. Наблюдаемая величина — расчётная минимальная дальность и вероятность сближения каталогизированного объекта со станцией (CelesTrak SOCRATES, при недоступности — резервно Space-Track `cdm_public`) как прокси-показатель обстановки по мусору. По той же логике объединяет космический мусор и сближения со спутниками/другими объектами — оба используют один и тот же источник и один физический механизм (каталогизированное сближение). Явно указано: это не индивидуальная вероятность попадания мелкого несопровождаемого фрагмента в космонавта — только показатель обстановки вокруг станции по отслеживаемым объектам.

Траектория, рассчитанная по SGP4, используется не только для карты: доля светлого времени окна (`daylight_fraction`) рассчитывается по фактической геометрии освещённости вдоль траектории и показывается как ограничение работ, отдельно от двух оцениваемых факторов риска (критерий Т2 — "расчёт траектории используется в анализе хотя бы одного фактора или ограничения работ").

## Сравнение окон и дат (критерий О3)

Два разных механизма сравнения, оба используют один и тот же движок рекомендации (`analysis._recommend`), чтобы логика "равнозначно/недостаточно оснований" была одинаковой в обоих случаях:

- **Период поиска начала** (поле в основной форме, 0–24 ч) — сравнивает несколько окон одинаковой длительности с разным временем начала вокруг ОДНОЙ выбранной даты. Результат — таблица «Сравнение окон ВКД» на основной странице.
- **Сравнить даты** (`POST /api/compare-dates`, кнопка «Сравнить даты» в интерфейсе) — сравнивает два ПОЛНОСТЬЮ РАЗНЫХ дня/сценария (например 10 мая и 21 мая) при общих длительности/периоде поиска/шаге. Каждая дата считается независимо через тот же `run_analysis`, что и обычный расчёт, затем окна обеих дат объединяются в один список и оцениваются той же функцией `_recommend` — так рекомендация одинаково честно обрабатывает оба случая: если у одной из дат данных не хватает, это видно по каждому окну отдельно, а не маскируется усреднением дат.

## Исторический режим (01.05.2024–30.06.2024)

Две различимые функции (по условиям задачи):

- **Космическая погода** (`assess_historical` в `space_weather.py`): используются только уведомления NASA DONKI с `messageIssueTime` не позже выбранного момента отсечения. Более поздние уведомления явно исключаются из расчёта (`dropped_future` в логах/заметках) и доступны отдельно через `verification_signals()` только для проверки — они никогда не попадают в рекомендацию. Проверено тестами (`tests/test_space_weather.py`).
- **Сближения/MMOD** (`assess_historical` в `conjunction.py`): CelesTrak SOCRATES сам по себе не хранит архив (только скользящий прогноз на ~7 суток вперёд), поэтому без Space-Track сервис честно возвращает `data_sufficient=False`. Но если заданы `EVA_SPACETRACK_IDENTITY`/`EVA_SPACETRACK_PASSWORD`, используется официальный архив Space-Track `cdm_public` — он хранит полную историю, поэтому строгий "прогноз из прошлого" возможен и для этого фактора: запрос фильтруется по времени публикации самого CDM (поле, аналогичное `CREATION_DATE`, обнаруживается динамически так же, как и остальные поля схемы) не позже момента отсечения — точно та же дисциплина, что и у DONKI. Проверено тестами (`tests/test_conjunction.py`, `tests/test_spacetrack.py`).

Историческая орбита: без учётных данных Space-Track (`EVA_SPACETRACK_IDENTITY`/`EVA_SPACETRACK_PASSWORD`) траектория помечается как **реконструкция** по ближайшим доступным элементам и никогда не выдаётся за проверяемый исторический прогноз положения станции (см. `orbit.reconstruction_note`).

## Надёжность (критерий Т6)

- Кеш на диске с TTL на каждый источник; при сбое источника используется последний успешный ответ с явной отметкой давности и ошибки (`SourceCache.get`, `tests/test_cache.py`).
- Отказ источника никогда не превращается в "риска нет" — при отсутствии данных фактор помечается `data_sufficient=False` / `insufficient_data`, и это учитывается при формировании рекомендации (`tests/test_analysis.py::test_all_sources_failing_yields_no_false_safe_recommendation`).
- В интерфейсе (раздел «Источники данных») каждый источник можно **заморозить** (не обновлять, но продолжать показывать закешированное) или **отключить** (не использовать вовсе) — удобный способ проверить поведение системы при деградации данных, как того требует задание.
- Параметры разных запросов не смешиваются: `AnalyzeRequest` полностью самодостаточен, кеш ключуется по источнику, а не по запросу пользователя.
- Каждая попытка получить данные повторяется до 3 раз с короткой паузой перед тем, как источник считается недоступным (`SourceCache.get`) — сглаживает разовые сетевые сбои (обрыв соединения, кратковременная медлительность), но не маскирует постоянную недоступность источника: после исчерпания попыток поведение то же самое (кеш с пометкой давности или явная ошибка).
- Тайм-аут на установление соединения (`EVA_HTTP_CONNECT_TIMEOUT_SECONDS`, по умолчанию 6с) отделён от тайм-аута на весь ответ (20с) — недоступный/заблокированный хост завершается ошибкой быстро, а не ждёт полный тайм-аут на каждой из 3 попыток.
- Траектория и оба фактора (космическая погода, сближения) запрашиваются параллельно, а не по очереди — при недоступности одного источника остальные не ждут его в очереди, и общее время ответа ограничено самым медленным источником, а не суммой всех.

### Известная проблема: CelesTrak и бесплатный хостинг (Render и подобные)

CelesTrak периодически блокирует или сильно ограничивает трафик с IP-адресов облачных/датацентровых провайдеров (задокументировано в их форумах поддержки) — в том числе на общих IP бесплатных тарифов Render и похожих PaaS. Если после деплоя `/api/analyze` стабильно падает с `celestrak_gp: ConnectTimeout`, а не локально — это, скорее всего, не баг кода, а именно эта блокировка.

Для режима «Текущая обстановка» сервис теперь сам перебирает источники орбитальных элементов по цепочке, ничего настраивать не нужно:

1. **CelesTrak** (основной, лучшая свежесть данных).
2. **Зеркало CelesTrak на GitHub** (`raw.githubusercontent.com`, обновляется каждые ~8 часов) — не требует регистрации, включено всегда. Это не независимый источник (просто republish данных CelesTrak), но работает на инфраструктуре GitHub, которую блокируют/режут на порядки реже, чем небольшой волонтёрский CelesTrak — по факту именно это и спасает на Render. Давность данных честно показывается в интерфейсе (`age_hours`).
3. **Space-Track** — только если заданы `EVA_SPACETRACK_IDENTITY`/`EVA_SPACETRACK_PASSWORD` в `.env`.

Если все три источника недоступны, ошибка покажет причину по каждому из них, а не только по CelesTrak. Дополнительно, если и это не помогло:

Для CelesTrak SOCRATES (сближения/MMOD) готового зеркала на GitHub не существует — это расчётный, а не просто republish-able продукт. Единственный резерв: Space-Track `cdm_public` (те же `EVA_SPACETRACK_IDENTITY`/`EVA_SPACETRACK_PASSWORD`, что и выше), автоматически задействуется, если SOCRATES недоступен. Так как точные названия полей этой схемы нельзя было проверить заранее (см. `clients/spacetrack.py`), они читаются "вживую" перед каждым запросом через служебный метод Space-Track `modeldef`, а не берутся из захардкоженного списка — сигналы с этого резервного источника помечаются пониженной уверенностью (`low`), а не выдаются как эквивалент основного источника.

- Указать `EVA_HTTP_PROXY` в `.env` (тот же механизм, что и для NASA, см. выше) — но учтите, что прокси на другом облачном провайдере (тот же Cloudflare Workers) может оказаться таким же датацентровым IP и тоже попасть под блокировку; обычным residential/VPN-адресам обычно везёт больше.
- Перейти на платный тариф Render (другой пул исходящих IP) или другой хостинг.
- Подождать — блокировки CelesTrak по сообщениям пользователей иногда снимаются сами через некоторое время.

## Запуск

### Локально

```bash
cd backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env   # опционально: свой NASA_API_KEY, учётные данные Space-Track
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Открыть `http://localhost:8000/` — интерфейс и API работают на одном порту (FastAPI отдаёт статику `frontend/`).

### Docker

```bash
docker compose up --build
```

### Тесты

```bash
cd backend
python3 -m pytest
```

52 теста покрывают: SGP4-пропагацию и её согласованность с эпохой TLE, поведение кеша при отказе/заморозке/отключении источника, строгое отсечение по времени публикации в историческом режиме (и для DONKI, и для Space-Track `cdm_public`), разбор и дедупликацию SOCRATES, резервный переход GP на зеркало/Space-Track и SOCRATES на Space-Track `cdm_public` в обоих режимах (включая живое определение схемы полей и корректный URL `modeldef`), явную обработку неверного логина и превышения лимита DONKI, DONKI как независимый источник в текущем режиме, движок сравнения окон/дат (включая `/api/compare-dates`), корректный вклад сближений в оценку окна (регрессия на точечный TCA-сигнал), корректный и откалиброванный горизонт влияния сигналов DONKI/оповещений SWPC на окно в текущем и историческом режимах (три отдельные регрессии — слишком короткий запас по умолчанию, несогласованность с глубиной просмотра назад, и излишне широкий запас, "склеивающий" все сравниваемые окна в одну оценку) и корректную обработку случая "нет оснований для рекомендации".

### Эксперимент (критерий Т5)

```bash
python -m app.experiments
```

или `GET /api/experiment` (кнопка «Показать эксперимент» в интерфейсе). Сравнивает метод команды (взвешенная серьёзность по типам уведомлений DONKI) с наивным базовым подходом (бинарный флаг "есть хоть одно уведомление") на выраженном событии — экстремальная геомагнитная буря 10–12 мая 2024 г. ("буря Gannon", G5) — и спокойном контрольном периоде 1–2 июня 2024 г. Оба периода — внутри поддерживаемого исторического диапазона.

## Воспроизводимость (критерий Т8)

Каждый расчёт получает `result_id` (UUID) и сохраняется на диск (`data/results/<result_id>.json`) целиком: параметры запроса, момент отсечения, версия алгоритма (`algorithm_version` в `config.py`), все сигналы с источниками и правилами, окна и рекомендация. `GET /api/results/{id}` восстанавливает сохранённый расчёт, `GET /api/export/{id}` отдаёт архив `report.json + windows.csv + signals.csv + README.txt`. Содержимое выгрузки полностью совпадает с тем, что показано в интерфейсе (общее поле `result_id` и одна и та же модель ответа).

## Ограничения и допущения (честно, как того требует задание)

- **TEME→ECEF**: только поворот на GMST (без учёта прецессии полюса/нутации) — ошибка не более нескольких сотен метров, пренебрежимо мала на фоне точности самого SGP4.
- **Освещённость**: цилиндрическая (не коническая) модель тени Земли — стандартное огрубление для грубой разметки "день/ночь" вдоль трассы, не для точного расчёта частичного затенения.
- **Положение Солнца**: низкоточная формула Astronomical Almanac (~0.01°), этого достаточно для теста освещённости.
- **S/G/R-scale**: публикуются NOAA посуточно, что грубее требуемого 6-часового горизонта — точное время начала/окончания внутри суток помечается как неопределённое (`is_time_uncertain=True`).
- **CelesTrak SOCRATES в историческом режиме**: недоступен без Space-Track — сознательно помечается недостатком данных, а не подменяется текущим прогнозом.
- **CelesTrak SOCRATES недоступен из сети деплоя (тот же блок, что и у `gp.php`, см. выше)**: сервис автоматически пробует резервный источник Space-Track `cdm_public`, если заданы `EVA_SPACETRACK_IDENTITY`/`EVA_SPACETRACK_PASSWORD`. Если и он недоступен (или учётные данные не заданы), колонка «Полнота данных» в сравнении окон становится красной («недостаточно данных») для каждого окна — это честное поведение, а не баг: фактор сближений/MMOD не подменяет реальную недоступность источника выводом «риска нет» (сводная оценка ниже так и требует — хорошие данные по одному фактору не маскируют нехватку по другому). У SOCRATES нет готового зеркала вроде GitHub-зеркала для орбитальных элементов (это расчётный, а не просто republish-able продукт), поэтому резерв — именно Space-Track, а не CDN-зеркало. Точный формат полей `cdm_public` не был захардкожен из памяти (не подтверждён напрямую против живого API — сам space-track.org недоступен из нашей среды разработки); вместо этого клиент читает реальную схему через служебный метод Space-Track `modeldef` непосредственно перед каждым запросом (см. `clients/spacetrack.py::fetch_cdm_conjunctions`/`parse_cdm_events`) и помечает такие сигналы пониженной уверенностью (`low`).
- **DONKI DEMO_KEY**: ограничение ~30 запросов/час, причём **общее на всех анонимных пользователей `api.nasa.gov` сразу**, а не только на этот сайт — легко словить `429 Too Many Requests` даже при умеренном использовании. Получите бесплатный личный ключ на https://api.nasa.gov (мгновенно, нужен только email) и укажите его в `EVA_NASA_API_KEY` — у личного ключа лимит на порядки выше. При 429 сервис теперь явно называет причину и подсказывает это в самом сообщении об ошибке (`clients/donki.py::DonkiRateLimited`), а не просто падает с сырым HTTP-статусом.
- **Доступность api.nasa.gov из некоторых сетей/регионов**: NASA DONKI используется и в историческом режиме, и в `/api/experiment`, и в режиме «Текущая обстановка» (см. таблицу источников выше). Если именно `api.nasa.gov` недоступен из вашей сети, есть два варианта:
  1. Указать `EVA_HTTP_PROXY` в `.env` — через него пойдут все запросы сервиса.
  2. Указать `EVA_DONKI_BASE_URL` на свой собственный бесплатный реверс-прокси (см. `tools/donki-proxy-worker.js` — разворачивается на Cloudflare Workers за 5 минут, без чужих посредников и без риска, что кто-то чужой увидит ваш API-ключ).
  Намеренно не зашиваем в проект чей-то чужой публичный бесплатный прокси: такие адреса недолговечны и небезопасны (через них шёл бы ваш API-ключ), а сломавшийся на защите хакатона прокси — хуже, чем его отсутствие.
- Сервис не переводит показатели космической среды в индивидуальную дозу конкретного космонавта или вероятность повреждения скафандра — это отдельная задача, требующая эксплуатационных моделей, которых нет в открытых данных.
